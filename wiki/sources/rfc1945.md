# RFC 1945 — HTTP/1.0

원본: `raw/rfc1945.txt`. rfc-editor.org에서 받은 원문 그대로다 (2026-10-15).
1996년 5월에 나온 Informational 문서다 (raw/rfc1945.txt:9-13). subject가 기준점으로 제안한 버전이다. 강제는 아니다 (raw/subject.md:123).
현재 HTTP 규칙은 [[sources/rfc9110]]·[[sources/rfc9112]]가 기준이고, 이 문서는 HTTP/1.0 요청을 받을 때와 "1.0 기준점"의 범위를 판단할 때 쓴다.

## 핵심

- 실험적 구현이 아니면 요청마다 클라이언트가 연결을 열고, 서버는 응답을 보낸 뒤 닫는다 (raw/rfc1945.txt:420-422).
- 요청줄에 버전이 없으면 HTTP/0.9 형식으로 본다 (raw/rfc1945.txt:668-679). 0.9 요청은 `"GET" SP Request-URI CRLF`이고 헤더가 없다 (raw/rfc1945.txt:1190).
- HTTP/1.0 서버는 0.9·1.0 요청을 이해하고, 클라이언트가 쓴 버전으로 응답해야 한다 (raw/rfc1945.txt:694-703).
- 메서드는 대소문자를 구분한다 (raw/rfc1945.txt:1302). 모르거나 구현하지 않은 메서드는 501 (SHOULD, raw/rfc1945.txt:1313-1315).
- 본문이 있는 HTTP/1.0 요청은 `Content-Length`가 있어야 한다. 연결 종료로는 요청 본문의 끝을 알릴 수 없기 때문이다. 없으면 400 (SHOULD, raw/rfc1945.txt:1657-1663). POST도 같다 (raw/rfc1945.txt:1763-1765).
- status code 목록에 405·411·413·414·505 등은 없다 (raw/rfc1945.txt:1487-1501).
- 파일 시스템에 URI를 그대로 대응시키는 서버는 `..`로 의도한 범위 밖에 접근하는 것을 막아야 한다 (must). 설정 파일·스크립트 코드 같은 내부 파일도 보호해야 한다 (raw/rfc1945.txt:2809-2823).
- DELETE는 본문이 아니라 부록 D에 있다. 부록 D는 일부 구현에서 쓰지만 일관되게 구현되지 않은 기능이다 (raw/rfc1945.txt:3185-3199, raw/rfc1945.txt:3223-3226).

## 이후 RFC와의 관계

- RFC 9110: 서버는 요청의 메이저 버전 이하에서 자신이 따르는 가장 높은 버전으로 응답해야 한다 (SHOULD, raw/rfc9110.txt:2054-2056). HTTP/1.0 요청에 `HTTP/1.1`로 응답할 수 있다는 뜻이다. RFC 1945의 "같은 버전으로 응답"과 다르다.
- RFC 9112: 이름 기반 virtual host를 구현하는 서버는 HTTP/0.9 지원을 꺼야 한다. 0.9처럼 보이는 요청은 대부분 잘못 만든 1.x 요청이다 (raw/rfc9112.txt:2215-2221).
